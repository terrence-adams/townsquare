## 1. `curl -fsS -m 10 "$URL" -o "$TMP"` fails closed — CONFIRMED, measured

I stood up a one-shot local HTTP server returning 500 with a body, and ran the script's exact construct (`if ! curl -fsS -m 10 "$URL" -o "$TMP"; then ...`) against it. Result: curl exited 22, the `if !` branch fired, and — more strongly than either document assumed — **`$TMP` was never created at all**, not just left empty. The error body never touched disk anywhere, let alone `authorized_keys`.

Two precisions worth adding:
- **Don't over-state "$TMP is never created" as universal.** I measured it for a clean, fast 4xx/5xx (status known from headers before any body streams). A slow 200 that blows past `-m 10` mid-transfer is a different failure path (timeout, not `-f`'s status check) and could in principle leave partial bytes in `$TMP`. It doesn't matter: the script's failure branch does `rm -f "$TMP"; exit 1` before the while-loop that writes to `authorized_keys` ever runs, so the "never touches authorized_keys" conclusion holds regardless of what, if anything, landed in `$TMP`. State the conclusion on the control-flow guarantee (rm-then-exit precedes the write loop), not on an unverified claim about `$TMP`'s exact contents on every possible failure shape.
- **"Touches" needs one qualifier.** Lines 20-21 (`mkdir -p ...; [ -f "$AK" ] || { : > "$AK"; chmod 600 "$AK"; }`) run unconditionally, *before* the curl call. On a brand-new host's very first run, if the registry happens to be unreachable on that first invocation, the script still creates an empty `authorized_keys` (correct permissions, zero keys) before failing. That's not the pollution/lockout hazard anyone is worried about, and it's inert given password SSH stays enabled fleet-wide — but "fails closed before anything touches authorized_keys" is very slightly overbroad as literally written. I'd say "before anything is *added to or removed from* an existing authorized_keys" instead.
- **The "misleading error message" note in v3 §2 is slightly overstated.** `-S` (`--show-error`) means curl prints its own diagnostic to stderr even in `-s` mode — in my test it was `curl: (22) The requested URL returned error: 500`, printed immediately before the script's own generic "registry unreachable" line. For a timeout it would instead say "Operation timed out..."; for DNS/connect failure, "Could not resolve host" / "Connection refused". So the *full* stderr stream already distinguishes network failure from HTTP 400+ from timeout — the ambiguity is specifically in the script's own bespoke echo text, not in what actually reaches stderr. Cheap fix if it's ever worth a Request: capture `rc=$?` and fold it into the script's own log line so the two facts don't have to be manually correlated by whoever's debugging a 3am stall.

## 2. Empty (HTTP 200, zero-line) pull is harmless — CONFIRMED, measured end-to-end

Local server returning 200 with `Content-Length: 0`. Ran the full script logic (loop + `sort -u -o`) against a pre-populated `authorized_keys` containing two keys. Result: `added=0`, and the file's SHA-256 was **identical before and after** (`c682ed40a4d2dd0019334bd8a605799f255c3f4d2fed35a4b3a6870828064689`, both times). Confirms: `-f` only fires on 400+, a 200-empty exits 0, the loop runs zero times, and because the only writes to `$AK` are additive (`>>`) or a dedup-rewrite (`sort -u`) that preserves the existing set, nothing is lost. The `[ -z "$key" ] && continue` guard (line 34) also means a feed with stray blank lines behaves identically to a truly-empty feed — it doesn't get treated as an empty-string "key."

One addition, squarely in my lane: this is harmless to `authorized_keys`, but it's a **silent-success blind spot for anyone monitoring only the script's exit code**. A registry that's up but serving a persistently-empty or broken-but-200 feed produces exit 0 and a cheerful "0 key(s) added" line — indistinguishable, to exit-code-only monitoring, from a completely uneventful run where there was simply nothing new to add. That's a different failure class from the 400+/timeout case (which at least surfaces via nonzero exit + stderr). This is exactly why P1/P3's approach — comparing feed bytes/hashes/line-counts directly rather than trusting exit codes — is the right instrument for *this* check; I'd flag the general blind spot as a longer-term fleet-monitoring item (e.g., alert on line-count drift against a rolling expectation), separate from and not gating decision 6.

## 3. sshd skips unparseable lines rather than refusing the file — CONFIRMED (expertise, not measured here)

This is well-established, long-standing OpenSSH behavior, consistent across the versions in common use: `sshd` walks `authorized_keys` line by line looking for a match to the presented key; a line that fails to parse (bad base64, bad options syntax, an HTML/JSON error body pasted in, etc.) simply never matches, gets logged at most at debug/verbose level, and processing continues to the next line. It does not abort the file and does not deny other, well-formed keys in the same file. This is exactly why "polluted, not locked out" is the right characterization, and it's also why the same reasoning extends to a *structurally valid* key of a disabled/unsupported type (e.g., an algorithm excluded by `PubkeyAcceptedAlgorithms`) — also skipped, not fatal.

One scope note I want to add explicitly since it's adjacent and easy to conflate: this skip-and-continue behavior is about *content parsing*. It's separate from sshd's *StrictModes* permission check on `~/.ssh` and `authorized_keys` (group/world-writable → sshd refuses to use the file at all, logged as "bad ownership or modes"). That's the one way a whole-file refusal genuinely happens — and the script avoids it correctly (`chmod 700` on `.ssh`, `chmod 600` on the file, both lines present and unconditional). So the "not a lockout" conclusion holds cleanly for the content-pollution scenario in play here.

I have not stood up a real sshd to test this in this review — doing so credibly (real keys, a deliberately malformed line, an actual auth attempt) is more setup than a document review warrants, and it's the one claim here I'm confirming from established knowledge rather than a fresh test. If the fleet wants this moved from "confirmed by known behavior" to "measured," a cheap way is a throwaway account/VM with a garbage line appended ahead of a valid key and one real login attempt — low-value enough relative to the confidence level that I wouldn't prioritize it, but flagging it as available if anyone wants zero residual doubt.

## 4. `while IFS= read -r key` (no `|| [ -n "$key" ]` guard) drops the feed's last key when it lacks a trailing newline — CONFIRMED, measured

Reproduced the exact construct against `printf 'keyA\nkeyB\nkeyC'` (no trailing newline) vs `printf 'keyA\nkeyB\nkeyC\n'` (with one):
- Unguarded, no trailing newline: only `keyA`, `keyB` processed. `keyC` — the last line — silently dropped. Total 2.
- Unguarded, with trailing newline: all three processed. Total 3.
- Guarded (`read -r key || [ -n "$key" ]`), no trailing newline: all three processed. Total 3.
- Guarded, against a fully empty file, under `set -eu`: runs cleanly, `total=0`, no unbound-variable error — confirms the proposed fix doesn't introduce a `nounset` hazard on the empty-feed edge case.

This is real, exactly as described, fleet-wide (standard POSIX `read` behavior, not shell-implementation-specific — I tested under bash-as-sh here; the same EOF-without-newline/exit-status behavior is what makes the `read || [ -n "$var" ]` idiom universally necessary and documented across dash/ash/ksh/POSIX sh, not a bash quirk), and correctly scoped by v3 as live-or-latent depending on one byte, unrelated to `claude-app`, and correctly triaged as a Request to bishop rather than something gating decision 6. The proposed one-line fix is textbook-correct and sufficient on its own.

One addition: since `/register` is the single source of authority here, the *registry* could just as easily fix this at the source — guarantee the served `/authorized_keys` response always ends in `\n` (append one if missing, before writing the response body). That's a one-place, one-time fix that closes the defect fleet-wide immediately, versus the client-side fix which only takes effect on each host as it happens to re-pull the corrected script. I'd suggest the Request to bishop offer both: fix the client loop (defense in depth, correct regardless of feed hygiene) and fix the feed's trailing byte (closes it centrally, faster). Neither supersedes the other.

## 5. The P1-P5 check design (section 4) — sound overall, with concrete additions

**What I think is genuinely well-built, from having run syncs like this:**
- **It doesn't trust the journal alone.** P3 cross-checks actual served bytes (feed, `/mesh`) independently of the journal's narrative, and only uses the journal to adjudicate attribution ("was claude-app's write the only write"). Audit logs lag or misreport far more often than the artifacts they describe — anchoring safety on byte comparison of the real artifact, with the journal as a secondary corroborating signal, is the right layering.
- **The two-tier immediate (P3) + settled (P4a, 10 min later) structure is exactly right**, including for a risk neither document raised: if `/authorized_keys` were served through any caching layer, an "immediately after" comparison could show a false negative for a brief window. Nothing here suggests a cache exists (a bare `192.168.2.3:8789` on a private LAN reads as a small directly-exposed service), but even if one did, P4(a)'s later re-check already covers it — this is a case where the existing design is robust to a risk it didn't explicitly name.
- **P5 row 3's framing — retiring removes the row from the feed but does not strip the key from hosts that already synced it (A19) — is exactly right, and I want to underline it.** This is the single easiest thing to get wrong in a "just roll it back" instinct: given the sync script is additive-only-never-remove (confirmed above), a registry-side retire is not a host-side undo. Correctly gating any host-side removal on a separate Sensei go is the correct call.
- **"Have the undo ready before P2"** — confirming the exact `/retire` payload before sending the risky change, not after — is good release discipline I'd want from any change of this shape.

**Concrete gaps/improvements, from the same experience:**

**(a) Add a full `/registry` hash, not just venom's and claude-app's fields.** P1 hashes `/authorized_keys` and `/mesh` but only spot-checks specific fields of `/registry` (any claude-app row, venom's stable fields). That leaves a real, if narrow, gap: an unanticipated bug that silently mutates some *other* agent's row wouldn't be caught by anything in P1-P4 as written. Since v3 already defines a "stable fields" projection (agent, vendor, model, binding, section, os, shell, role, status, pubkey, host_address) to exclude the fields expected to churn on their own (`last_source`, `updated_at`, `applied_at`, `flags`), I'd extend that same projection across *every* row in `/registry`, concatenate, and hash it at P1/P3/P4 alongside the two existing hashes. That gets full-blast-radius coverage at the cost of one more read, without the false-alarm risk a naive full-response hash would carry from other agents' routine heartbeat/timestamp churn.

**(b) Tighten the wording of P5's applicability gate.** As written: "Rows 2 and 3 apply only when the journal shows claude-app's write as the only write since P1. Otherwise, row 5 applies." Literally, this scopes the gate to rows 2-3 only — row 4 isn't mentioned, so a strict reading lets row 4 ("only /mesh or claude-app's own fields differ → keep, note, Request") fire even when a concurrent unrelated write muddies attribution, which seems like an oversight rather than intent (row 4's own observation is just as confoundable by a concurrent write as rows 2-3's are). I'd change it to "Rows 2, 3 and 4 apply only when..." unless it's deliberate that row 4's low-stakes action is meant to be usable regardless of attribution — in which case say so explicitly rather than leaving it to the gate's grammar.

**(c) Row 1's "nothing was written" is an assumption, not something P5 verifies.** A rejected POST *should* mean nothing was written if the service validates before writing, but that's bishop's code, not confirmed here. Doesn't change the row's action (stop and report either way), so it's low stakes — but I'd word it as "confirm via `/registry` and `/journal` that nothing was written, then stop and report" rather than asserting the state as given.

**(d) Clarify "Both feed captures" in P3.** P1 takes 4 feed captures total (2 endpoints × 2 time-points). P3 says "Both feed captures are byte-identical to P1" — I read "both" as the two *endpoints* (`/authorized_keys` and its `?exclude=venom` variant), each compared against its own already-confirmed-stable P1 value, not as "compare against both P1 time-points" or "you need four separate comparisons." I'm confident that's the intended reading, but it's worth a one-line parenthetical for whoever executes this cold.

**(e) Confirm `/retire` is itself journaled before leaning on post-retire journal reasoning.** §3 states (reported-by bishop) that "the journal records every accepted write" — presumably retire counts, but that's stated explicitly only for `/register`. Worth a one-look confirmation (an existing retire event in journal history, if one exists) before P5 rows 2/3's "retire at once and re-capture" leans on the same "exactly one entry newer" logic for the retire step itself.

**(f) `sort -u "$AK" -o "$AK"` rewrites in place, non-atomically, on every run — separate from, and narrower than, the trailing-newline issue.** I measured the hash changing on a no-op dedup pass (rewritten every time, as v3 says). Coreutils' own documentation confirms sort fully reads all input before opening the output path for writing (so it can't corrupt its own read), but it opens/truncates the *same* file rather than writing to a temp path and renaming into place — meaning there's a real, if extremely brief, window where a process reading `authorized_keys` at the exact same moment (most relevantly, sshd handling an inbound connection) could see a truncated or partially-rewritten file. For a file this small the window is on the order of milliseconds, and the failure is self-healing (retry the SSH connection). Not worth gating anything on, but worth banking alongside the trailing-newline fix as a future hardening candidate: `sort -u "$AK" -o "${AK}.tmp" && mv "${AK}.tmp" "$AK"` would make the rewrite atomic via rename.

**(g) Minor operational-friction note, not a soundness defect:** if the registry serves `/registry` or `/mesh` rows in a non-deterministic order (e.g., unordered iteration with no explicit sort), two successive reads with zero real changes could still produce different bytes/hashes. P1's own stop rule ("if the two feed captures differ, stop and retake") already fails toward *more* caution in that case, not less — so it's not a correctness risk, just a possible source of extra stop-and-retakes if the underlying serialization isn't stable.

**(h) Affirming, not correcting: P2's emphasis on the `agent` field is the right one, and here's the mechanical reason why the blast radius is bounded.** Given `/register` overwrites any named row with no ownership check, a mistyped `agent` value colliding with an existing agent doesn't create a stray row, it silently clobbers that agent's live row — and because `pubkey`/`host_address` are empty in this payload, the practical effect of such a collision (via the sync script's additive-only design) would be "that agent's key stops being offered to any host that hasn't yet synced it," not "already-authorized hosts lose access retroactively." Same A19 logic as row 3, applied to a different trigger. Worth keeping in mind if the payload check in P2 is ever relaxed.

**(i) The row-3 exposure window (P2 to P3, seconds; P2 to P4(a), 10 minutes) during which some host's own sync cadence could coincide with a bad key transiently reaching the feed — accept as designed, don't tighten further.** Given the payload carries no pubkey, this can only trigger via an actual service bug, and even then the fleet's standing password-SSH-stays-on decision bounds the downside to pollution, not lockout. I don't think this warrants trying to pause fleet-wide sync cadence during the registration window (which the registry couldn't enforce anyway — cadence is host/cron-side) — "detect promptly, defer remediation to Sensei" is proportionate to a low-probability, bounded-severity, bug-gated risk.
