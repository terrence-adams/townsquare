## 1. Assigned U-items

### U4 — no DB-level constraint. Build proceeds; do not come back to ip-man.

Read `registry/db.py`'s `SCHEMA` in full (lines 14–40). `agents.section` is `TEXT NOT NULL DEFAULT 'host_bound'`; `agents.binding` is `TEXT DEFAULT 'unknown'`. No `CHECK`, no foreign key, no SQLite enum (SQLite has none natively, and nothing simulates one). The four `ALTER TABLE ... ADD COLUMN` statements in `RegistryDB.__init__` (lines 67–71, wrapped in `try/except sqlite3.OperationalError: pass`) add `pubkey`, `host_address`, `applied_at`, `flags` as plain `TEXT DEFAULT ''`, no constraint either. I went further than a read of the `CREATE TABLE` block: I grepped the whole `services/registry` tree, case-insensitive, for `CHECK|TRIGGER|CONSTRAINT|ENUM`. The only hits are `check_same_thread` (a `sqlite3.connect` kwarg name), a comment using "check" as an English verb, a `validate_ac.py` helper literally named `check()`, and a test function named `test_register_triggers_publish_when_enabled` (English "triggers", not a SQL trigger). **There is no `CREATE TRIGGER` anywhere in the service, and no application-level check outside `schema.py` that would reject `'offsite'`.**

**Verdict on U4: confirmed clean. The build proceeds exactly as ip-man assumed — this does not need to come back to him.**

One data-architecture observation for later, explicitly *not* for this fix: the entire "binding may only be one of N shapes" invariant lives in `schema.py` application code, not the database. That's precisely why the residual risks the design already accepts (S5's races, the legacy path, a direct DB edit) are all *possible* — nothing at the storage layer would refuse a bad value even today. A `CHECK (section IN (...))`/`CHECK (binding IN (...))` retrofit is real hardening, but SQLite has no `ALTER TABLE ADD CONSTRAINT`; adding one now means a rebuild-the-table migration (create-new, copy, drop, rename) — exactly the class of change ip-man's own note says should stop the build and come back to him. I'm not proposing it for this fix (R8 is right to leave `db.py` alone), just naming it as a legitimate future item for bishop's thread, since it's the direct cause of several residuals the design already correctly chose to accept rather than fix now.

### U10 — confirmed: the legacy path cannot write `pubkey` or `host_address`, traced end to end.

`crier.py`'s `_KNOWN = ("section", "annotation", "vendor", "model", "binding", "os", "shell", "role", "status")` (lines 119–120) excludes both fields. `_keep_known(fields)` (123–124) is a plain dict comprehension: `{k: v for k, v in fields.items() if k in _KNOWN}` — no aliasing, no pass-through of unlisted keys. It is applied at the one and only call site that writes to the DB via this path: `self.db.upsert(agent, source=..., node=..., at=..., writer=by, **_keep_known(rec))` (line 305).

I traced the full path, not just the tuple, because `_extract_fields` (206–231) has a branch that is *not* pre-filtered: if the crier event itself carries an `ev["registry"]` or `ev["fields"]` sub-dict with an `agent` key, `_extract_fields` returns `dict(ev[key])` **unfiltered** — so a `pubkey` key could in principle be present at that point. It then flows to `poll_once` (250–317), where `validate_record` is called on a `RECORD_FIELDS`-filtered *copy* of `fields` (lines 291–293), but `normalize_record` is then called on the **original, unfiltered** `fields` (line 301) — a real (pre-existing, out-of-scope) inconsistency between what gets validated and what gets normalized. None of that matters for U10's question, though, because the **very last step before the DB call** — `_keep_known(rec)` at line 305 — drops any key not in the 9-tuple regardless of how it got there. So the conclusion holds, and it holds for a slightly stronger reason than "the tuple excludes it": **every route into `db.upsert` from this path is gated by the same final allow-list, so there is no way for `pubkey`/`host_address` to reach storage through `crier.py`, however they entered `_extract_fields`.** `host_of` (line 195, `ev.get("by") or ev.get("from")`) is attribution only — it supplies the `source`/`writer` string, never a field value, and has no bearing on this question.

**Verdict on U10: confirmed against the function bodies, not inferred.**

### U11 — confirmed, and I found the same volatility applies one layer wider than the addendum scoped it.

Read `journal.py` and `publisher.py` in full. The journal line written by `Journal.record` (`entry` dict, lines 73–83: `seq, at, op, agent, source, applied_at, before, after, outbox`) is append-only and never rewritten (`read()` only parses; nothing in the module ever opens the journal file for writing except `record`'s own append). **`publishing` is not stored in the journal line at all** — `app.py`'s `/journal` handler bolts it on per-request: `e["publishing"] = _publisher.status_for(e.get("outbox", ""))` (app.py line 287), and `Publisher.status_for` (publisher.py 173–186) reads a *separate* mutable ledger (`publish_state.json`, loaded fresh via `_load_state()`) plus a filesystem check (`os.path.exists(.../published/<name>)`). Since francis's D3 established that a container restart triggers an immediate, unconditional outbox-drain attempt, a PENDING entry's `publishing` status can legitimately flip to PUBLISHED between the pre-deploy and post-deploy reads with zero new registrations. So: comparing `/journal`'s newest entry by `op`/`agent`/`applied_at` rather than raw bytes is the right fix, and it holds up against the actual code.

**What I'd add:** the *same* response envelope carries two more fields sourced from that same mutable ledger, at the same volatility, for the identical reason — `outbox_pending` (`len(_publisher.pending_files())`, app.py line 302) and `publisher.pending`/`publisher.published` (`Publisher.summary()`, publisher.py 188–193). A restart-triggered drain changes these counts exactly as it changes a single entry's `publishing` status. If francis's runbook step 6 intends "everything else from step 2 is byte-identical" to cover the *whole* `/journal?limit=5` response body (not just the newest entry), it will trip the same false-positive the addendum already correctly diagnosed for the per-entry field. **Recommend francis's runbook explicitly exempt `outbox_pending` and `publisher.pending`/`publisher.published` from the byte-identical check, for the same stated reason (D3's automatic drain), alongside the newest entry's `publishing` field.** This is a runbook refinement, not a design defect — it doesn't touch R1–R8 and doesn't need to go back to ip-man; it's for francis's Implement (3).

### U12 — confirmed: nothing in the existing suite needs updating for the new message or the 3-element tuple. One real test-ordering hazard found for ronda.

I read all 705 lines of `tests/test_registry.py`, not just grepped it. Every assertion that touches a section/binding error uses a substring check — `any("section" in e for e in errs)`, `any("binding" in e for e in errs)`, `any("contradict" in m for m in e)` — never an exact-message or tuple-cardinality assertion. `SECTIONS` is never referenced by name anywhere in the test file (confirmed by grep, zero hits). `test_render_tables_seven_cols_no_version` calls `render.render_tables([...], [])` with exactly two positional arguments; per R6 that remains valid once `offsite_rows` becomes a defaulted trailing keyword. **No existing test needs to change for R1's new message or R1/R6's larger tuple/signature.**

**A concrete, actionable ordering hazard for ronda-rousey, independent of the above:** this file's own runner (bottom of the file) executes tests via `fns = [v for k, v in sorted(globals().items()) if k.startswith("test_")]` — **alphabetical by function name, not definition order.** String-sorting means `"test_t10"` sorts *before* `"test_t2"` (`'1' < '2'` as the first differing character). The addendum's own test list is written as a sequence with real cross-test dependencies — T4/T4b/T4c/T4d, T5, T7 are each specified as "after T1," i.e., relying on a *different, earlier* test having already created the `claude-app` offsite row. If ronda names new tests `test_t1_...` through `test_t12_...` and reuses this file's runner, T10–T12 would run *before* T2–T9, breaking every "after T1" precondition. Note that the **existing** suite already avoids this trap: `test_retire_emits_journal_and_outbox` and `test_register_triggers_publish_when_enabled` each create their own prerequisite row inline (`retirebot`, `publishbot`) rather than depending on a different test's side effect having already run. **Recommend the new tests follow the same established pattern — each test creates its own offsite row inline (or via a small shared helper called at the top of each test) rather than relying on "after T1" as a cross-test dependency** — whether or not they land in this file. This is more robust than renaming/padding, since it also survives someone running a single test in isolation for debugging.

**One more test-design note that follows directly from finding (b) in §3 below:** the adversarial cases `" offsite"` and `"offsite\n"` (called for in the original design's §4) are only a meaningful test if they exercise the full round trip — write via `POST /register` with the padded value, then check what's actually *stored* and what the feed does — not just a unit call to `offsite_violations()`/`validate_record()` with the padded string held in memory. See §3(b) for why the distinction matters here specifically.

## 2. Core design re-derivation (not just the U-items)

### R3 restated: re-derived against the actual `app.py`/`schema.py` control flow, and it holds.

I did not accept the addendum's correction at face value; I re-traced all three of Q3's original naive-fix paths against the code I read myself, with the addendum's proposed insertion applied (`existing = db.get(str(rec["agent"]).strip()); errors = schema_mod.offsite_violations(existing, rec)`, placed between the current lines 185 and 186 — confirmed those are exactly `validate_record`'s `if not ok: return ...400` and `rec = schema_mod.normalize_record(rec)` respectively, matching the addendum's citation letter for letter).

- **Path 1** (`binding: offsite` + a key in one body): `existing` is `None` or irrelevant; R3a's merged-pubkey check sees the body's own non-empty key directly → 400. Holds.
- **Path 2** (a later partial `{agent: claude-app, pubkey: K}`, no binding, against an already-offsite row): this is the path that broke ip-man's *original* R3 placement, because by the time a post-normalize check looked at "the merged binding," `normalize_record` had already defaulted the missing binding to `"unknown"`, so the check never saw `"offsite"` and never fired. Restated R3 avoids this specifically because **R3b keys off the *existing row's stored* binding, not the incoming/normalized value** — `existing.binding == "offsite"` is true regardless of what the body does or doesn't say, and the body carries no non-empty binding, so R3b fires and rejects *before* `normalize_record` ever runs. I confirmed this by reading `normalize_record` itself: `out.setdefault(...)` / the `if not str(out.get(f,"")).strip(): out[f] = "unknown"` loop only ever *replaces* a field when it's already empty — it cannot retroactively un-fire a check that already ran and returned before it was called. **This genuinely closes the hole; the fix is placement plus which side (existing vs. incoming) R3b reads, not just "run it earlier."**
- **Path 3** (`{agent: X, binding: offsite}` against a keyed host row, key not cleared): R3a's merged pubkey falls back to the existing row's value when the body doesn't carry the field, catches the leftover key → 400. The same body with explicit empty-string clears → merged pubkey is the body's `""`, not an error → 200, matching T5 exactly.

**Verdict: R3 as restated closes what it claims to close. I found no fourth path.**

### R6 (`render.py`): backward-compatible against every current caller — I enumerated all of them, not just the two the addendum names.

`grep -rn "render_tables\|render_snapshot"` across the *entire* Wonderland checkout (not just `app.py`) turns up exactly three call sites for `render_tables` (`app.py:162` in `/registry?format=md`, `app.py:231` in `/tables`, and `tests/test_registry.py:264` in `test_render_tables_seven_cols_no_version`) and exactly one for `render_snapshot` (`tests/test_registry.py:96`, a direct unit test — confirmed no production route calls it; the module docstring's mention of `/snapshot` routes is aspirational text with no matching `@app.route`, verified against my own full read of `app.py`'s route table). None of the other services in the repo (`crier`, `revere`, `townwatch`, `townwatcher`) import `registry.render` at all. The two `app.py` sites are the ones the addendum plans to edit (adding the third list and `offsite_rows=off`); the test file's call passes exactly two positional args and is untouched by the fix, which is fine because `offsite_rows=None` (the new trailing keyword default) reproduces today's output exactly — I confirmed the "when None/empty, byte-identical" claim by reading the planned body: the appended section is gated by a plain truthiness check (`if offsite_rows:`), so `None` and `[]` take the identical old branch.

**Verdict: R6 is backward-compatible against every caller I could find in the repo, confirmed by an exhaustive grep, not just the two sites already named.**

### F3 (recency guard) — confirmed, with the actual mechanism named.

I traced both directions rather than accept the one-line claim. `db.upsert`'s staleness guard (`db.py` 103–111) is **all-or-nothing at the field-set level**: when a write is stale, `vals = {}` wholesale — not a per-field suppression. I walked both a stale write that tries to convert a row *to* offsite while leaving a key unset in the merge, and a stale write that tries to convert a row *away from* offsite while adding a key: in both cases, because R3 runs before `db.upsert` and evaluates the request on its own (correct) merits, and because a stale `db.upsert` call either applies the *entire* incoming field set or *none* of it, a stale write can never leave a row in a partially-applied, invalid combination (e.g., binding changed but key not cleared, or vice versa). The row simply stays exactly as it was. **Confirmed: it errs safe, and the reason is the atomicity of `vals={}`, not merely that "a stale write changes no field" as a general assertion** — it's specifically that it changes *all* targeted fields or none, which is what actually matters for a two-field invariant like S1.

## 3. Findings from my own fresh read (not assigned, offered as the data-model specialist coming at it cold)

**(a) Windows `core.autocrlf` hash hazard — see §0.** Concrete, verified, and operationally relevant to francis's runbook Step 4 (local hash vs. post-copy NAS hash). Recommend hashing via `git show`/`git cat-file` (or explicit LF normalization) rather than a raw Windows-checkout `sha256sum`, for whoever actually produces and verifies the three changed files.

**(b) Non-agent field values are stored unstripped — pre-existing, not introduced by this fix, but the new code must defend against it explicitly.** `validate_record` strips `binding` (and `agent`) into a *local* variable purely to run its regex/enum checks; it never writes the stripped value back into `rec`. `normalize_record`'s defaulting loop only replaces a field when it is *empty after stripping* — a non-empty-but-padded value (e.g. `"offsite\n"`, `" offsite"`) passes through untouched. Nothing between there and `db.upsert` (which also never strips field *values*, only the `agent` parameter — confirmed at `db.py` line 98 `agent = agent.strip()`, which has no analogue for `binding`/`vendor`/`model`/etc.) ever cleans it. So **a request with a padded binding can store the padding verbatim in the `binding` column.** This is pre-existing (identical exposure exists today for `"portable\n"` or `" host:X"`), and it does **not** break the offsite security guarantee, because the design's own prose already calls for stripping at every comparison point ("the *stripped* binding," used throughout R3a/R3b/R4) — but that means the guarantee now rests on bruce-lee remembering to `.strip()` at each of the (roughly four) new comparison sites (`offsite_violations`'s two checks, R4's feed filter, and `derive_section`'s new offsite branch), not on the stored data already being clean, because it structurally isn't guaranteed to be. This is squarely relevant to gsp's S1–S4 sign-off too, not just an implementation nit — worth him seeing this framing, not just "the design says stripped."
- Concrete recommendation for bruce-lee: strip at each new comparison site explicitly (the design already says to; just naming the exact reason it's load-bearing here, not decorative).
- Concrete recommendation for ronda-rousey: the `" offsite"` / `"offsite\n"` adversarial cases should go through `POST /register` and then check the **stored row and the feed**, not call the validation functions directly with the padded string held only in memory — the interesting risk is specifically about what round-trips through storage and back.

**(c) `parse_md.py` would silently *misclassify*, not just drop, a future "Offsite agents" section — sharper than "would need the new heading."** The addendum already defers this correctly (it's kano's Queue 3 reissue work, and the live DB is non-empty so `_seed_if_empty()` won't fire on this deploy regardless). I traced the actual mechanism: `parse_registry_md`'s section-tracking only resets `section = None` on an **H2** heading that isn't H3 (`if line.startswith("##") and not line.startswith("###")`); an *unrecognized* H3 heading like `### Offsite agents` doesn't match that condition, so it falls through without resetting state. If such a heading is ever added directly after the existing `### 2.2 Portable subagents` table in a future reissued document, any pipe-table rows under it would continue to be parsed with `section` still `"portable"` — silently mislabeling offsite agents as portable on a future reseed, rather than simply being ignored. The exposure is bounded, though: `parse_registry_md`'s row dict never has a `pubkey`/`host_address` key at all (its 7-column schema doesn't parse one for *any* section), so this cannot leak a key through a reseed — it's a classification/labeling defect for kano's future work, not a security one. Worth relaying precisely so the eventual `parse_md` update fixes the reset logic, not just adds a recognized heading.

**(d) Confirmed (supports, doesn't undermine, the design's own residual-risk framing): the deployed Flask app really is multi-threaded by default.** I checked this rather than assume it, because it's the precondition for S5's "two concurrent `/register` calls" residual being a real, not merely theoretical, exposure. `app.py`'s `app.run(host="0.0.0.0", port=...)` (line 341) passes no `threaded=` argument; I read Flask 3.1.3's actual installed source (`Flask.run`) and confirmed `options.setdefault("threaded", True)` — threaded mode has been the default since Flask 1.0. So the race window the design already accepts as a residual (two writes to a new name, one binding it offsite, one carrying a key with no binding, interleaved before either lands) is a genuine property of this deployment, not something accidentally ruled out by single-threading. This is a confirmation, not a new gap — I'm recording it because it was cheap to check and it removes a "but is this even possible" doubt from the residual's write-up.

**(e) `section` is a stored, derivable-but-not-enforced-derived column — relevant context for gsp's default-deny call, not a vote on it.** `schema.py`'s own docstring states the intended invariant plainly: `"section is DERIVED from binding... not an independent source of truth."` But `db.py`'s schema stores `section` as its own independent `TEXT` column (U4), populated by whichever write path last touched the row, and nothing enforces that it stays in sync with `binding` — bishop's own row (`binding: unknown`, `section: host_bound`) is a live instance of exactly this drift, not a hypothetical. From a pure data-modeling standpoint, that makes `binding` the more trustworthy field to gate on (it's the one the code's own comment calls authoritative), while `section` is a cache that has already been observed to go stale. This is offered as input to gsp's still-open default-deny question (checking `section == host_bound AND binding != offsite` vs. `binding != offsite` alone): either is defensible, but if he's weighing "which field to trust more," the data model's own stated authority hierarchy (and the one proven drift instance) points at `binding`. I'm not making that call — it's his — just handing him the schema-level reason it's not a close call between the two fields' reliability.
