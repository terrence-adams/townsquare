OVERALL SHAPE
The projector models the board correctly as an append-only event log over an implicit thread graph: `parent:` is a foreign key that can never be enforced at write time (D1 forbids refusal), so the projector's real job is reconstructing a referential-integrity report at read time. It does that well for the cases the design and the 61 tests anticipated. My findings are mostly about edges of that same integrity model that weren't fully reconciled — validation is uneven between two fields that both name a thread id, and two of the projection's three top-level buckets (`no_project`, `intake`) have zero test coverage even though `intake` is the very first stop every real ask makes under the design's own intake workflow (v1 doc s8).

FINDINGS, RANKED

1. `parent:` bypasses the canonical grammar that `references:` goes through, and this actively produces a false claim in the output.
   `references:` values are validated/normalized by `_thread_ids()` (projector.py:146-161), which completes free text into a full filename (`.000-OPEN.txt` or `-OPEN.txt`) and re-parses it through the canonical `parse_filename` -- so a garbage or annotated token is provably not a thread id, not just "not found." `parent:` (used directly in `resolve()`, projector.py:305-313) is instead compared as a raw stripped string against dict keys, with no such normalization.
   Verified: `parent: "TS-20260101-venom-800 (its Epic)"` against a real thread `TS-20260101-venom-800` produced `parent_not_found` with `detail={"parent": "TS-20260101-venom-800 (its Epic)", "thread_exists": False}` -- and `thread_exists: False` is factually wrong; the thread genuinely exists. This is an easy real-world mistake given the sibling `references:` field's own convention uses exactly this "id (annotation)" shape in the same header block.
   Recommendation: route `parent:` through `_thread_ids()` the same way, requiring exactly one clean TS id; if the free-text token doesn't collapse to exactly one, flag that distinctly (e.g. `parent_malformed`) instead of a `parent_not_found` that can lie about whether the thread exists.

2. A collided thread (two unrelated `.000` opens sharing one id, D23) that itself carries `level:` is still promoted into the tree as one ordinary node, not held out the way a collided *parent reference* already is.
   The design and the module docstring already special-case a collided id named as someone else's parent: "The child is reported and shown at top level, not guessed under either open" (projector.py:38-39, tested in test_flags.py test_3). But when the collided thread is itself a tracker item, `nodes[tid]` still gets built from a G3 "newest wins" merge across the two unrelated physical posts, with only the separate `thread_collided` flag as a signal (projector.py:298-303, no `continue` after that flag).
   Verified: two colliding `.000-OPEN` opens -- one `by-venom` (`level: epic, project: townsquare`), one `by-forge` (`level: feature, project: kollective`) -- produced one merged node (`level: epic`, arbitrarily the filename-sort winner) placed under `projects["townsquare"]`, plus one `thread_collided` flag. The docstring's own "choices the design does not pin" section names the collided-*parent* case but not this symmetric collided-*node* case, so this looks like a genuine blind spot rather than an accepted trade-off.
   Recommendation: either exclude a collided thread from `nodes` entirely (report `thread_collided`, don't place a synthetic node), or explicitly document this as an accepted, asymmetric trade-off so a future reader doesn't assume the two cases are handled the same way.

3. `level: unscoped` (intake) items only land in `result["intake"]` if their `parent:` fails to resolve; if it resolves to something real, the item silently disappears from `intake` and shows as a buried child instead.
   `intake.append(node)` only runs inside `for tid in roots:` (projector.py:420-427); if an unscoped item's `parent:` happens to resolve, it gets an `edge` entry and is no longer a root, so it never reaches that loop at all.
   Verified: an `unscoped` item with `parent:` pointing at a real Epic did not appear in `result["intake"]`; it showed as a child under that Epic in `projects`, flagged only with `nesting_violation` (a separate section of the output).
   Why it matters: `intake` is meant to be ip-man's single visible holding pen for asks awaiting scoping -- every real ask starts at `level: unscoped` per v1 doc s8. The design states unscoped items "have no parent" as an assumption, not an enforced rule (D1 forbids refusal), so a copy-paste artifact or a mid-scoping transition could put an ask in exactly this state, and it would vanish from the one list built to surface it.
   Recommendation: decide and test one of (a) bucket by `level == "unscoped"` unconditionally regardless of whether `parent:` resolves, or (b) keep current behavior but say so explicitly -- right now "Nothing is dropped silently" (module docstring) is true only if you already know to check the flags list.

4. No mechanism exists to explicitly detach a `parent:` (or clear any newest-wins field) once set. An empty value is defined not to carry the field (by design, A5), so it can only be overridden by pointing at a *different* real value, never cleared back to "no parent."
   Verified: writing a later event with `parent: ""` left a Story nested under its original Epic, unchanged.
   This is a consistent consequence of documented rules working together, not a projector bug -- but "a re-parented Story moves between Features" is explicitly named and tested as intended behavior, and there's no symmetric way to move a Story back to top-level. Worth naming to the design owner: if that's ever needed operationally, the convention will need a sentinel (e.g. `parent: none`) the parser treats as a carrying value.

5. Duplicate `for:`/`acceptance:`/`references:` (AUX_KEYS) are silently dropped with no flag at all, unlike duplicate TRACKER_KEYS which raise `duplicate_header_key` -- this is explicit, documented scope (A5 scopes the flag to the five tracker keys), not an oversight. Verified: a duplicated `for:` on a Feature produced zero flags. For Stories this is partly self-covering via `story_not_ready`; for Epics/Features there's no equivalent check, so the same underlying problem (a field silently rendered unreadable by duplication) is invisible on those two levels. Low priority, worth a one-line note since `for:` is the accountability field.

6. Two test-coverage gaps, both confirmed by execution rather than just noticing an absence:
   a. No test uses the real production Archive shape, `Archive/<YYYY-Qn>/` with no per-board subfolder (per TSD s8) -- every archive test uses the fixture's own assumed `Archive/<board>/` shape (boardfixture.py's docstring candidly admits this). I confirmed the shipped code handles the real shape correctly (`os.walk` recursion is subfolder-name-agnostic, so it doesn't actually matter which convention is real) -- not a live bug, but cheap to close and exactly what the task brief asked me to check.
   b. Neither `result["no_project"]` nor `result["intake"]` has a single direct test anywhere in the 61. Finding 3 above is precisely the kind of bug a test on `intake` would have caught.

7. The entire same-sequence tie-break and the `last_activity` rollup rest on local filesystem mtime as a stand-in for Drive's `createdTime` (projector.py:171-173, 230-231, 372-382). ronda-rousey's boardfixture.py docstring already candidly flags this as mirroring what the real trial does too (a Drive-Desktop-synced local mirror, not the Drive API) -- I'm not raising a new risk, just confirming and sharpening it: worth one cheap empirical check on venom before trusting `last_activity` for more than a rough signal -- compare a few real synced files' local mtime against their true Drive-reported modified time, since a full local resync would otherwise make every file's `last_activity` read as "just now."

8. Minor: `story_not_ready`'s `parent_not_feature` reason fires identically whether the parent is real-but-wrong-level or entirely unresolvable (missing/collided/cyclic) -- verified across my self-parent and cycle-adjacent checks, where `story_not_ready`, `nesting_violation`, and `cycle`/`parent_not_found` all fired together correctly, but the DoR reason code alone doesn't distinguish them. Only matters if someone consumes `story_not_ready` in isolation. Also: ip-man's design watch-for "cache by path, since files never change" (aimed at a reported 20s full-mount-read timeout) isn't implemented -- `build_projection` is a stateless full rescan every call. Not a correctness issue and may not matter for a single-shot CLI, but it's an explicit design ask the shipped code doesn't address; flagging for whoever owns the post-trial NAS/Viewer deployment where repeated reads matter more -- that's Jet Li/francis-ngannou territory, not mine to fix here.

WHAT'S SOLID (specific, not just "looks good")
- Filename parsing is genuinely centralized: `_scan`/`consider` call only `registrar.app.filename.parse_filename`, no second filename grammar exists anywhere.
- `_thread_ids()`'s two-step completion (try `.000-OPEN.txt`, then `-OPEN.txt`) is a clean way to validate both a bare thread id and a "thread.seq (annotation)" reference through the one canonical grammar with no hand-rolled reimplementation of thread-id shape. I verified it directly: `_thread_ids("TS-20260925-venom-004")` and `_thread_ids("TS-20260925-venom-004.002 (evidence)")` both correctly resolve to `[("TS-20260925-venom-004", "TS")]`, and garbage text returns `[]`.
- The `(seq, mtime, filename, path)` sort correctly makes sequence primary and time only a tie-break for a genuine duplicate sequence, matching the Crier's rule rather than naively sorting by time.
- Cycle detection is correct not just for the one tested 2-node case but for two untested shapes I traced and then verified by execution: a single node naming itself as its own parent (correctly flagged as both `nesting_violation` and a 1-member `cycle`), and a non-cycle node whose parent is itself a cycle member (correctly stays nested under the cut-loose cycle member rather than also being cut loose).
- The header-reading logic is deliberately NOT the canonical `filename.py`'s `read_header`/`check_header` -- and that's correct, per the design's own explicit watch-for (avoid `check_header`'s zero-padding defect and its raise-on-duplicate-key behavior). The module draws the right boundary: one shared grammar for filenames, a separate, intentionally lenient, well-justified local implementation for header text.
- `project` (strict single top-down inheritance, never restated) versus `repo` (nearest-ancestor-with-override) are correctly implemented as two different rules matching the design's field table exactly, not conflated into one generic "inherit from parent" helper.
