2. DOES R1's DEPARTURE FROM MY FIX LOSE ANYTHING, AND DOES IP-MAN'S REASONING HOLD?

It holds. I re-tested my own original recommendation ("route `parent:` through `_thread_ids()`, requiring exactly one clean TS id, flag only otherwise") against the same three shapes, by execution: `_thread_ids()` collapses the bare id, the annotated value, and the event-id value to the *identical* result, `[('TS-20260101-venom-800', 'TS')]`. Nothing I meant by the fix is lost. The diagnostic value I was after — telling the filer which id their mistake actually named — survives intact via `ids_found` (sourced from the same `_thread_ids()` I'd have used), it's just reported instead of silently acted on. The only thing dropped is auto-repair-at-read-time, and the ruling's own stated reason for dropping it — that Q2 exists specifically to count filing errors, and a value that silently self-corrects is invisible to that count — is a consideration my original review didn't weigh (I was reviewing for data-architecture soundness, not trial-measurement epistemics), and it's a correct override for a 30-day *instrumented* trial. I also checked the one operational cost of R1's choice (a malformed parent is placed nowhere until someone notices and fixes it, rather than placed correctly right away) and found the ruling already names this exact trade-off as a rejected alternative with a stated, bounded reversal condition ("real filings hit this more than once... decided in the post-trial amendment, with the flag counts as evidence") — that's a sound way to hold a reversible position open, not a loose end.

One thing worth confirming since it wasn't spelled out in the "Why": the equality check (not just "does it parse") is load-bearing, not decorative. (by execution) A value like `"TS-20260101-venom-050.0-OPEN__foo"` completes and *fullmatches* `parse_filename` on the first try — the grammar's `rest` group swallows the trailing text — returning `thread = "TS-20260101-venom-050"`, which is only a prefix of the original value. Without the equality check this would wrongly validate as bare. With it, it's correctly rejected. I also confirmed a second-id shape (`"TS-...-800 TS-...-801"`) and both a POSIX- and Windows-style path prefix are all correctly rejected the same way — the ruling's "no new regex... rejects annotations, event suffixes, second ids and paths" claim holds for all four named shapes, by execution, not just by the ruling's own assertion.

I'd route this to the same backlog bucket as F4/F5 rather than gate this pass on it.
- An unscoped item can still legitimately be nested-*under-by* another, well-formed item; R3 doesn't touch this direction and doesn't need to. (by execution) A Feature naming a still-`unscoped` ask as its `parent:` today gets nested under it (appearing inside `intake`'s own node, in its `children` list) with `nesting_violation` correctly flagged on the Feature (`expected_level: epic, actual_level: unscoped`). R3's text is scoped to the unscoped item's *own* placement as a child ("not nested under another item") and says nothing about it acting as a parent — so this is unchanged by R3, before or after. I checked whether this is a new blind spot and concluded it isn't: it's the same "reported, never refused" pattern already deliberately built and tested elsewhere — `test_nesting.py::test_feature_parent_pointing_at_a_story_is_a_nesting_violation_reported_not_refused` (by reading, confirmed the name and the assertion: the mis-nested item is still placed in `children`, just flagged) is the identical pattern with a different flavor of "wrong-level parent." Worth naming explicitly so it's a documented, deliberate non-gap rather than an unconsidered corner, not worth a rule change.
